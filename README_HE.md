# ATLAS2 Follow NEO — גרסה 18.0.1 / REAL-TIME HARD

## תזמון שליחת TCP — שלב 3

בלשונית **Control / Search**, בקבוצה **TCP command timing**, בוחרים
**Send rate (Hz)** ולוחצים **Apply TCP send rate / save**:

| קצב יעד | מרווח בין פקודות |
|---|---|
| 20Hz — ברירת מחדל | 50 מילישניות |
| 25Hz | 40 מילישניות |
| 30Hz | 33.33 מילישניות |

בחרו והחילו את הקצב לפני Enable והתחלת הניסוי. הבחירה נשמרת להפעלה הבאה
וחלה על שליטה ידנית, ריקוד ו־HARD. אין צורך ב־APK חדש. להפעלה ממשיכים
להשתמש ב־`RUN_FOLLOW_NEO.cmd`.

התזמון משתמש במועדים קבועים ובשעון מדויק, וקורא את החלטת המעקב העדכנית
אחרי ההמתנה. אין תור פקודות להשלמת פערים. הקצב בפועל עשוי לרדת עם עומס
או אישורים מאוחרים; סף אישור TCP נשאר **250 מילישניות** בכל שלוש האפשרויות.
שלב 2 ומנגנוני הבטיחות נשמרו. ב־HARD אין לוגים או מדידות אבחון חדשות.

להשוואה התחילו ב־20Hz עם אותם ערכי מהירות ומעקב, ובהמשך שנו רק ל־25Hz
או ל־30Hz. מחוץ ל־HARD נשמרים הקצב שנבחר וחותמות ניסיון שליחה מדויקות
לצורך ניתוח המרווחים; אין להסיק מקצב השליחה בלבד את קצב התגובה של הרחפן.

## רציפות במעבר בין NanoTrack ל־BoT-SORT — שלב 2

לכל מקור נשמרת היסטוריית מהירות ועיקול משלו. גם כשהמיקום מגיע מ־Nano,
מדידות YOLO המאומתות מעדכנות את היסטוריית BoT-SORT. כאשר Nano אינו תקף,
עוברים מיד למיקום BoT-SORT; אין ערבוב קואורדינטות ואין המשך על סמך Nano פג תוקף.
המעבר עצמו אינו עוד סיבה למחיקת היסטוריית העיקול של המקור התקף.
החלפת זהות/דור, עוגן Nano חדש או פער ארוך עדיין מחייבים בניית ראיות מחדש.

לאחר נפילה מ־Nano, החזרה אליו דורשת שתי תמונות שונות ורצופות שעברו את
כל בדיקות האימות, במרווח שאינו עולה על 100 מילישניות. בזמן האימות ממשיכים
ב־BoT-SORT; לא מוסיפים המתנה שבה הרחפן עומד. קריאה חוזרת של אותה תמונה
אינה נחשבת תמונה חדשה. רכישה ראשונה נשארת במסלול האימות הקיים.

עלייה בפקודת הסיבוב באותו כיוון יכולה להתרכך למשך עד 100 מילישניות
לאחר החלפת מקור קרובה ומאומתת, בקצב עלייה של 2 יחידות סיבוב מנורמלות לשנייה.
הפחתה, אפס, היפוך כיוון או שינוי גדול במיקום אינם ממתינים לריכוך.
מגבלות ההתקדמות קדימה נבדקות מול המיקום ודרישת הסיבוב המקוריים,
לפני הריכוך. שמירת מרחק, ספי הזמן, הגבלות הצד והחיפוש נשארים בתוקף.

השיפור פועל עם **NanoTrack primary position (Dance)** במצב **guarded**,
בהפעלה רגילה דרך `RUN_FOLLOW_NEO.cmd`. אין צורך ב־APK חדש או בשינוי ערכי ניסוי.
בלוג רגיל, `control_position.reason = nano_reentry_confirming` מציין אימות חזרה;
`centering_control.yaw_requested` ו־`position_handoff_limited` מסבירים ריכוך סיבוב.
ב־HARD עדיין אין כתיבת לוגים או איסוף מדידות אבחון.

לניסוי הבא השאירו את מהירויות הצירים, GMC ושאר ההגדרות ללא שינוי, ובדקו
אותו מסלול של קו ישר וסיבובים. מדידות הבדיקות המקומיות אינן הוכחה לשיפור בטיסה.

## המתנה בטוחה בהשהיית TCP זמנית — שלב 1

במצב HARD, איחור באישור פקודת תנועה מעבר ל־250 מילישניות עדיין גורם
לשליחת פקודת אפס ולחסימת תנועה חדשה. במקום לצאת מיד לממשק, HARD יכול
להישאר פעיל עד שנייה אחת מתחילת ההשהיה, על אותו חיבור TCP.
**זו תקרה להתאוששות, לא המתנה קבועה ולא עיכוב נוסף בריקוד תקין.**
כשהאישורים מגיעים אפשר להתאושש מיד, בלי לחכות לסוף השנייה.

החזרה דורשת תשובות מסודרות לכל הפקודות הממתינות ואישור לפקודת האפס,
ואחריהם תמונת וידאו, החלטה ואימות NEO אמיתי חדשים. עד אז לא נשלחת תנועה
חדשה. אין הארכה לתוקף תמונה, פקודה או זיהוי, ואין חיבור או Enable מחדש.
אישור אפס מהאנדרואיד אינו מדידה של עצירה פיזית של הרחפן.

אם ההשהיה אינה נפתרת בתוך השנייה, או שהתגובה נדחית/אינה ניתנת לשיוך,
HARD נפסק והשליטה משוחררת. שעון ההמתנה אינו מתאפס בכל תשובה או סבב.
רווח, Q, Esc, אובדן מיקוד, אות חיים חסר ותקלת וידאו עדיין מפסיקים HARD.
אין לוגים או מדידות אבחון בזמן HARD; סיבת חריגה מהחלון מוצגת לאחר היציאה.
מצב הריקוד הרגיל, אלגוריתמי המעקב ושירותי האנדרואיד לא שונו בשלב זה.

הפעלה כרגיל דרך `RUN_FOLLOW_NEO.cmd`; אין צורך ב־APK חדש או בשינוי הגדרות.
לניסוי השוואתי השאירו מהירות צירים, GMC ושאר הגדרות המעקב כפי שהיו.
בדקו שרווח מחזיר לממשק, ובהמשך האם השהיה קצרה מתאוששת בתוך HARD.
בדיקות TCP מדומה מכסות את מנגנון ההמתנה; הצלחתו בטיסה עדיין דורשת אימות.

## מקור מיקום מהיר לריקוד — שלב ראשון

בענף `yolo26s_integ_v17`, NanoTrack מאומת מספק את מרכז היעד בזמן הריקוד,
גם בין שתי תוצאות YOLO. הזיהוי והזהות נשארים באחריות YOLO ו־BoT-SORT.
רוחב וגובה המלבן, חותמת המדידה ושמירת המרחק נשארים במסלול הקיים;
גודל מלבן Nano אינו מדידת מרחק ואין מעבר לשמירת מרחק מסגמנטציה בשלב זה.

בלשונית **Settings** נוספה האפשרות **NanoTrack primary position (Dance)**,
מסומנת כברירת מחדל. היא פועלת כאשר מצב Nano הוא **guarded**.
לחצו `Apply / keep target` לאחר שינוי; להסרת השינוי לצורך השוואה,
בטלו את הסימון והחילו שוב. שאר ההגדרות והמהירויות השמורות אינן משתנות.
כאשר הריקוד פעיל, בשורת **Position** מוצג `nanotrack` או `botsort` והסיבה.

המיקום המהיר אינו מחדש את תוקף הזיהוי: עדיין נדרשת מדידת NEO אמיתית
בת עד 250 מילישניות, יחד עם תמונת Nano בתוקף, אותה זהות ואיכות מאומתת.
כשאין מיקום Nano תקף, הבקר מחשב מחדש מהמיקום הקודם של BoT-SORT;
פקודה ישנה שחושבה מ־Nano אינה מקבלת הארכת תוקף אוטומטית.
בפספוס YOLO נשמרים מסלולי ההמשך הקצר, העצירה והחיפוש הקיימים.

הבקר משתמש בזמני המקור של תמונות Nano לחישוב שינוי הכיוון. מהירויות
התמונה מחושבות בנפרד לכל מקור כדי שהחלפת המקור לא תיצור סיבוב מדומה.
חלון האימות של העיקול המוקדם נשמר גם בקצב תמונות גבוה.
בלוגים רגילים נוספו `control_position` ו־`position_applied`; בזמן HARD
אין רישום לוגים או מדידות אבחון. קצב הפקודות ופרוטוקול TCP נשמרו.

הפעלה כרגיל דרך `RUN_FOLLOW_NEO.cmd`; אין צורך בעדכון APK.
לניסוי ראשון השאירו את אותם ערכי מהירות ופיצוי מצלמה, והשוו סימון פעיל
וכבוי במסלול ובמהירות דומים. מדובר בשינוי מיקום לבקר, לא בהבטחה לקצב
מצלמה או לשיפור שכבר נמדד בטיסה.

## עיקול מוקדם והמשך קצר מאומת

כאשר `Coordinated turns` מסומן, תנועת מיקום עקבית ומאומתת בכיוון
שולי התמונה מאפשרת להתחיל סיבוב מוקדם בתוך TRACK. במצב החדש מקור המיקום
הוא Nano, בכפוף לאימות NEO אמיתי. ההקדמה מוגבלת ל־120
מילישניות ול־10% מחצי רוחב התמונה. אין מצב חיפוש חדש ואין רצפת מהירות:
חלון ההתקדמות, קצב הסיבוב בפועל ושמירת המרחק ממשיכים להגביל תנועה.
מדידה שמראה היפוך כיוון או חזרה למרכז מסירה את ההקדמה.

בפספוס קצר, פקודת קדימה וסיבוב שכבר אושרה יכולה לדעוך יחד, רק עם Nano
טרי ומאומת לאותו NEO, וידאו וכיוון טריים וללא חסימת מרחק או קצוות תמונה.
מסלול העיקול החדש מוגבל ל־350 מילישניות ממועד תמונת YOLO המקורית,
ולשינוי כיוון גוף של עד 20 מעלות. Nano אינו מחדש את השעון ואינו מגביר את
הפקודה. בדיקות אלו חוזרות בשער השליחה ובזמן המתנה לאישור TCP.
בסיום חלון העיקול, וקטור התאוששות ישן אינו מחזיר לפתע התקדמות קדימה;
נדרשת מדידה אמיתית חדשה. מסלול החיפוש הקיים נשאר כפוף למגבלותיו הנפרדות.

לוגים רגילים מכילים `centering_control.early_curve`, `curve_anchor`
ו־`curve_motion`; הרשאת ההמשך מסומנת `curve_bridge`.
ב־HARD אין לוגים או מדידות אבחון. חישובי אבחון שחצו כניסה או יציאה
מ־HARD מסומנים ללא מדידה (`null` / מילון ריק), במקום זמני חישוב שגויים.
תוצאת הזיהוי עצמה נשמרת, ומדידות האבחון מתחדשות בחישוב השלם הבא.

הפעלה: `RUN_FOLLOW_NEO.cmd`. אין צורך בהתקנת APK. TCP והאנדרואיד לא השתנו.
לניסוי השוואתי השאירו את מהירויות הצירים ושאר הערכים כפי שהיו, והתחילו
בתנועה ובסיבובים מתונים לפני זיגזג. איכות הטיסה דורשת בדיקת שטח.

## ניסוי פיצוי תנועת המצלמה

בלשונית `BoT-SORT` נוספו `GMC resolution (W x H)` ו־`Maximum feature points`.
ברירת המחדל והבחירה המקומית לניסוי זה הן `480x270` עם `400` נקודות.
הבחירות נשארות זמינות להשוואה; `640x360` הוא המצב הקודם,
ולבדיקת יותר פרטים אפשר לבחור `960x540` עם `400`.
זמינים גם `1280x720` ו־`1920x1080`, שהם ניסויים כבדים יותר, ועד `1000` נקודות.
יותר פיקסלים או נקודות אינם מבטיחים מעקב טוב יותר.

לחצו `Apply GMC / save` בין קטעי הניסוי. הכפתור שומר רק את שני שדות GMC;
שינויים ממתינים בשדות אחרים אינם מוחלים. היעד נשמר, אך כמו בהחלת הגדרות
רגילה, בקרת התנועה, שמירת המרחק וראיות Nano מתחילים מחדש וממתינים למדידה טרייה.
אחרי שינוי רזולוציה/נקודות נדרש גם זוג חדש של תמונות לחישוב פיצוי המצלמה.
כעת אפשר להיכנס ל־`REAL-TIME HARD`; ההגדרה חלה גם שם וללא לוגים בזמן HARD.
ההגדרות נשמרות להפעלה הבאה ובאירועי ההגדרות הרגילים שמחוץ ל־HARD.

הבחירה משפיעה רק על העותק הפנימי של פיצוי המצלמה, ולא על YOLO או זרם הווידאו.
אין מתיחה, חיתוך או הגדלה מעבר למקור. בזרם שאינו 16:9 המידה בפועל שומרת
על יחס המקור; הבחירה `640x360` שומרת על המסלול הקודם של רוחב מרבי 640.
לא נדרש עדכון APK.

בענף המקומי `yolo26s_integ_v16` נוסף מצב ניסוי ללא תצוגה, הקלטות, לוגים או
מדידות אבחון בזמן הריקוד. הפעלה דרך `RUN_FOLLOW_NEO.cmd` פותחת חלון
CMD ייעודי ואת הממשק הרגיל. לאחר חיבור הווידאו, חיבור המקלדת והפעלת Enable,
לוחצים **REAL-TIME HARD**. החלון מוסתר והריקוד מתחיל עם אותן הגדרות מעקב.
אין המראה אוטומטית; עוברים למצב זה לאחר בדיקת שליטה וטיסה ידנית.

**רווח**, **Q** או **Esc** במסוף עוצרים את הריקוד, משחררים שליטה ומחזירים
את הממשק הרגיל. גם אובדן מיקוד המסוף מפסיק את המצב. לחזרה לשליטה יש ללחוץ
Enable במפורש. הקלטות אינן מתחילות מחדש אוטומטית. אין נתוני אבחון או סרטונים
מקטע HARD, ולכן ההשוואה בו היא חזותית בלבד.

המסוף הייעודי נדרש כדי לבדוק שהמקלדת שייכת לחלון שלנו. חלון Windows Terminal
יכול להכיל כמה לשוניות או חלוניות, ולכן מיקוד החלון לבדו אינו מספיק.
ההפעלה הרגילה פותחת את המסוף העצמאי אוטומטית, גם מתוך Windows Terminal.
`RUN_FOLLOW_NEO_HARD.cmd` נשאר כקיצור דרך לאותה הפעלה. הממשק מוסתר רק לאחר
שהמסוף קיבל את המיקוד. מצב HARD דורש `--runtime process` ואינו
זמין במצב ההשוואה `inline`.

הבסיס הוא גרסה 14.1.1: הפעלה רגילה משתמשת בתהליך עבודה נפרד
מהממשק. TCP, המעקב ומצב REAL-TIME נשמרים. אין צורך בעדכון אנדרואיד.
אפשר להשוות למבנה הקודם בעזרת `run_lab.py --runtime inline`.
המבנה החדש משתמש ב־`run_lab.py --runtime process`, שהוא גם ברירת המחדל.
ראו את [מדריך הארכיטקטורה והניסוי](follow_neo/ARCHITECTURE_HE.md).

הסעיפים הבאים מתארים את מנגנוני המעקב מגרסה 14 שנשמרו:

העדכון הנוכחי הוא **`tracking-recovery-14`**, בענף **`yolo26s_integ_v14`**. הרצה רגילה דרך
`RUN_FOLLOW_NEO.cmd`, עם Nano במצב **guarded**; אין צורך בהתקנת תלויות.

| פקד | ברירת מחדל | טווח |
|---|---:|---:|
| BoT match cost (higher = looser) | 0.80 | 0.10–0.90 |
| BoT weak match cost | 0.50 | 0.10–0.70 |
| BoT tentative match cost | 0.70 | 0.10–0.85 |

ערך גבוה מקל על התאמת זיהוי למסלול, ואינו סף ביטחון או אישור תנועה.
ברירות המחדל שומרות על ההתנהגות הקודמת. **Apply / keep target** שומר
את הערכים ושומר את זהות המטרה, אך מאפס את היסטוריית הבקרה ואת Nano.
מומלץ להחיל בין ניסויים כשהריקוד כבוי. בדיקות הזהות, הטריות והרקע נשמרו.
אירוע `botsort_association` נכתב פעם אחת לכל תוצאת YOLO, עם סף, עלות
מיטבית, עלות ההתאמה שנבחרה והבחנה בין עלות גבוהה מדי לתחרות על זיהוי.

דגימת הווידאו שומרת כעת פריים מפוענח אחרון אחד עד מועד הפרסום הבא,
ומחליפה אותו אם הגיע פריים חדש יותר. ההמרה לתמונה מתבצעת בעובד נפרד
מהקליטה והפענוח. אין תור מצטבר או שכפול פריימים; זמן המקור נשמר,
ופריים שגילו מעל 100ms אינו מתפרסם. המפענח עצמו לא השתנה.
ב־`video_health` וב־`video_timing.sampling` נרשמים מספרי ההחלפות,
הפסילות והגיל בעת הבחירה. יעד 30 FPS אינו מבטיח 30 כאשר המקור מתעכב;
שמירה עד למועד הפרסום יכולה להוסיף המתנה קצרה שיש למדוד לצד הקצב.
בבדיקת אופליין קצרה עם הסרטון הקיים ותזמון הגעה מדומה התקבלו כ־29.8 FPS
בהגעה סדירה, וכ־27.1 לעומת 25.3 בהגעה לא סדירה. בתרחיש השני נוספו
כ־9ms בממוצע בין הפענוח לפרסום. אין זו מדידה של YOLO או של רשת חיה.
לשחזור הבדיקה: `analysis/benchmark_frame_sampling.py --video <clean.mp4>`.

בלשונית הצד החדשה **Motion** נמצאים פקדי ההתקדמות. ארבע הפינות האפורות
בחלון ובסרטון החיזוי מסמנות את גבולות מרכז המטרה למעקב רגיל. הרוחב
והגובה הם אחוזים מכל הפריים, ולא מגודל התיבה. לחיצה על **Apply motion / save**
מחילה ושומרת את כל הגדרות המעקב לטעינה בריצה הבאה; שינוי תוך כדי סשן
מאפס את הרשאת התנועה והיסטוריית הבקרה כרגיל, ולכן עדיף לכוון בין ריצות.

| פקד | ברירת מחדל | משמעות |
|---|---:|---|
| Window width / height | 80% / 70% | גבול חיצוני להתקדמות במעקב |
| Soft edge zone | 20% | האטה הדרגתית בחלק החיצוני של הטווח |
| Yaw demand ceiling | 50% | סף דרישת סיבוב מנורמלת; אינו אחוז מגבלת הציר |
| Yaw rate ceiling | 65°/s | סף מהירות הסיבוב המדודה להתקדמות |
| Forward rise | 2/s | קצב חזרת ההתקדמות עם ראיות NEO רציפות |
| Nano max age | 0.10s | גיל מרבי לתמיכה חזותית; ניתן להחמיר עד 0.04s |
| Require Nano… | לא מסומן | רצף YOLO טרי ומאומת יכול להשתמש בטווח הרחב גם בלי Nano זמין |
| Source-time motion budget | 1.0s | תפוגת התנועה המשולבת בחיפוש מזמן המקור המאומת |
| Forward / Side share | 35% / 20% | חלק ממגבלות הצירים שהוגדרו ב־Control / Search |
| Minimum look / Settling | 0.15s / 0.08s | זמני מינימום לתצפית כל 60° ולהתייצבות |

המלבן אינו מבטל מגבלות מרחק, זהות, טריות מידע או חשד לרקע. סמוך לגבול
ההתקדמות פוחתת בהדרגה; עלייה מחדש מוגבלת בקצב. בממשק ובלוג מוצג הגורם
המגביל: מיקום אופקי/אנכי, דרישת סיבוב, מהירות סיבוב או חוסר ראיות.
התקדמות Nano ללא מדידת YOLO חדשה שומרת על הטווח והזמנים המחמירים הקיימים.

שני זיהויי NEO חזקים וייחודיים יכולים לעדכן את כיוון החיפוש. בדיקת התנועה
מתחשבת בזמן בין פריימים, ורמז הכיוון נשמר עד 650ms מזמן המקור גם בזמן
בלימה. מסלול החיפוש שנותר מעודכן בהתאם; זמן החיפוש המקורי וגבולות הזווית
אינם מתחדשים. זיהוי בודד יכול לבלום סריקה, אך אינו מאשר זהות או התקדמות.

בשלב חיפוש קצר ניתן לשלב סיבוב, קדימה והצדה לכיוון שנשמר משלוש מדידות
אמיתיות. נדרשים היתר התקדמות קודם ו־Nano בריא בעת שמירתו. התנועה דועכת
ומסתיימת עד שנייה מהמדידה המקורית, ובכל מקרה לאחר שינוי כיוון מעל 35°.
פריימים של Nano, רמזי YOLO לא מאומתים וכניסה לחיפוש אינם מאריכים אותה.
וידאו או כיוון ישנים, קרבה, שינוי זהות, חשד לרקע או MINI מתחרה עוצרים אותה.
ביציאה מוכחת בצד המתאים ניתן להשתמש בהיתר המקורי גם לאחר סיום Nano,
רק אם בדיקות המראה, הטקסטורה והגאומטריה ברגע היציאה עברו. תיבה כתומה
לא מאומתת לבדה אינה מספיקה. שינוי כיוון בעקבות מועמד חדש ומבטי התצפית
עוצרים את התנועה; חיפוש ממושך נשאר סיבוב בלבד.

מבטי 60° עדיין דורשים סיבוב מדוד נמוך ושתי תוצאות YOLO מפריימים חדשים
לאחר ההתייצבות. 0.15s אינו הבטחה למשך העצירה הכולל: יש גם בלימה והמתנה
לתוצאות. קוד MSDKRemote, משקלי המודלים, קצב RC ומגבלות הצירים לא שונו.

תיאור העדכונים הקודמים להלן כפוף לשינויים שלעיל.

בעדכון `tracking-recovery-9` נוסף תיאום זמן בין תיבות YOLO ו־Nano:
כשיש רצף אמיתי של NEO, המערכת יכולה להשוות לתיבת Nano מאותו פריים מקור,
ולבדוק שהתנועה משם לתיבה הנוכחית סבירה. כך פער עיבוד אינו פוסל מיד מטרה
מהירה. התאמה היסטורית לבדה אינה מאשרת Nano שעבר לרקע.

חיפוש של 120° ומעלה כולל בלימה ומבט כל 60° מהכיוון שבו אבד היעד.
בכל מבט נדרשים קצב סיבוב מדוד נמוך ושתי תוצאות YOLO מפריימים חדשים
שצולמו לאחר ההתייצבות. סריקה כיוונית מסיימת מעגל אחד; סריקה ממורכזת
מבקרת בשני קצות הקשת. לאחר הכיסוי או תום התקציב החיפוש נעצר.

עם NEO מאומת ו־Nano בריא, מתאפשרת יותר התקדמות תוך כדי סיבוב;
תנועה הצדה עדיין דורשת מדידות עם פיצוי תנועת מצלמה. אחרי אובדן קצר
ניתן לשמר וקטור התקדמות מאומת, בדעיכה, עד **550ms מזמן מדידת YOLO
האחרונה ששמרה את הווקטור**. הוא מתוקן לפי שינוי כיוון הרחפן ונבדק שוב
בשליחה. התקרות הן 35% ממגבלת הקדימה ו־20% ממגבלת הצדה שב־GUI.
החלפת זהות, חשד לרקע, MINI מתחרה, תיבה חתוכה, קרבה, וידאו/מצפן ישנים,
שינוי כיוון מעל 35° או תפוגת זמן מבטלים אותו. מבטי ההתייצבות עוצרים תרגום;
חיפוש ממושך נשאר סיבוב בלבד. Nano אינו מחדש את זמן המקור.

להפעלה: `RUN_FOLLOW_NEO.cmd`, עם Nano במצב **guarded**. אין התקנה חדשה
וההגדרות השמורות אינן משתנות. פירוט האימות והלוגים ב־`UPDATE13_HE.md`.

התנהגות העדכונים הקודמים, בכפוף לתוספות שלעיל:

בעדכון `tracking-recovery-8` תוקן המעבר השגוי מ־SCAN ל־HOVER_WAIT בעת
אימות חלקי של המטרה. הכוונת שני זיהויי NEO בזמן אובדן קצר משתמשת בתקציב
החיפוש הקיים; הפסקת ההכוונה אינה מסיימת את החיפוש. חיפוש שכבר הסתיים
מקבל רק את המבט הקצר והמוגבל שהיה קיים, ללא פתיחת תקציב מלא מחדש.

במצב Nano **guarded**, רצף של לפחות שלוש מדידות NEO אמיתיות, חזקות
ועקביות יכול לשמר שליטה דרך YOLO כאשר התאמת המראה/זרימת הפיקסלים של
Nano חלשה. נדרשת התאמה בזהות, בדור הסשן ובתיבות, ללא MINI מתחרה;
סתירה ממשית, אובדן טקסטורה, גאומטריה חשודה ויציאה מהפריים ממשיכים לחסום.
מדידת YOLO חדשה אינה מונמכת לגישור אובדן רק כי Nano טרם אישר את זמן המקור
שלה, אם קיימות הראיות הנדרשות. גישור ללא זיהוי חדש עדיין מוגבל ל־350ms
קדימה ול־400ms סיבוב, ומוגבל במהירות ואינו מחדש ראיה סמנטית.

בתנועה הצדה, מדידת YOLO בגיל 150–250ms דורשת בנוסף אימות Nano חזותי
בריא מגיל עד 100ms, עם זהות תואמת ופיצוי תנועת מצלמה תקף. נדרשות עדיין
ארבע מדידות תנועה עקביות; חותמת זמן המקור אינה משתנה, ואובדן התמיכה
מבטל את התנועה הצדה גם לפני השליחה. חיפוש ממושך נשאר סיבוב בלבד.

נוספו ללוג `real_neo_evidence`, סיבת `fresh_yolo_pending_nano_anchor`,
`edge_search.candidate_scope` ופרטי התמיכה החזותית בתנועה הצדה.
לא נדרשת התקנה נוספת. הרצה: `RUN_FOLLOW_NEO.cmd`, עם Nano במצב guarded.
מגבלות הצירים נשמרו כפי שהוגדרו בממשק; תוצאות בדיקה על הקלטה אינן מדידת טיסה.

בעדכון `link-recovery-6` תוקנה ההתאוששות מהפרעות תקשורת:
אחרי השהיית ACK או heartbeat, באותו חיבור תקין עם הרשאת שליטה שאושרה,
אין בקשת `enable` חוזרת אוטומטית. עדיין ממתינים לכל התשובות ולאישור אפס,
דורשים heartbeat טרי ומשחררים מקשים שנלחצו בזמן ההשהיה. המראה/נחיתה
אינן משוחזרות והחזקת התנועה שלהן נשמרת. אישור ראשוני שלא הושלם,
דחיית פקודה, תשובות לא מזוהות או Enable מפורש אינם מדלגים על האימות.
סף השהיית RC נשאר 250ms וקצב השליחה נשאר 20Hz.

לאחר סגירת חיבור וידאו או שמונה שניות ללא נתונים/פענוח, הקליטה מנסה
חיבור מחדש ל־9999 עם השהיה עולה מ־0.5 עד 4 שניות בין ניסיונות.
כל ניסיון משתמש במפענח חדש. תוצאות YOLO, עקיבת BoT-SORT ו־Nano מהזרם
שנקטע נפסלות, ונדרש אישור מטרה חדש. מוצג `VIDEO RECONNECTING` ותמונה
ישנה נמחקת. הלוג מתעד `video_error`, `video_tracking_invalidated`,
`video_recovered` ומונה ניסיונות חיבור. זמן ההמתנה עדיין תלוי בטלפון
ובחזרת הזרם; חיבור מחדש אינו פותר הפרעות Wi-Fi או השהיה לפני המפענח.
MSDKRemote ומנגנוני מניעת הנעילה על הרקע לא שונו.

בעדכון `nano-handoff-5` תוקנו פערי תזמון בגישור במצב **guarded**:
אם מדידת YOLO עברה את גיל 250ms עד רגע השליחה, ההרשאה נבדקת מחדש
ויכולה לעבור לגישור Nano מוגבל במקום עצירת ביניים. כשהמדידה החדשה
מקדימה את האימות של Nano, נשמרת היסטוריה קצרה של אישורי התקדמות
כדי לבחור אישור שתואם לזמן המקור. מדידה חדשה שמורה לעצור מבטלת את
האישורים הישנים; האטה חדשה מגבילה גם את הפקודה הישנה.

חלונות הגישור נשארו 350ms להתקדמות ו־400ms לסיבוב, מפריים המקור,
עם פריים Nano מגיל עד 100ms. אין הארכה לפי זמן סיום העיבוד.
התאמת מראה חלשה ללא תמיכת תנועה עקבית בפיקסלי המטרה חוסמת הרשאת
Nano גם כשהציון שלו גבוה. התיבה יכולה להמשיך להופיע כ־UNVERIFIED;
תצוגה זו אינה אישור תנועה. מראה תקין אינו מחייב Optical Flow, כך שגם
רחפן מרחף יכול להישאר נתמך. גבולות מרכוז, קרבה, קצה ושליטה ידנית נשמרו.

לוג `flight_command.nano_handoff` מפרט את גיל המדידה בזמן השליחה,
סיבת המעבר, אישור ההתקדמות שנבחר וסיבת החסימה. ב־`tracking.timing`
נוספו זמני BoT-SORT ופירוט חישוב תנועת המצלמה. לצורך השוואת הריצה הבאה
יש להשאיר Nano במצב guarded; העדכון אינו משנה את מהירויות הצירים,
המודל או קצב הפקודות. בדיקות שחזור אינן מוכיחות תנועת רחפן חלקה בטיסה.

בעדכון `nano-continuity-4` מצב Nano הפעיל הוא **guarded**. בזמן Dance,
זיהוי YOLO אמיתי וחזק של NEO יכול לתקן אובדן שיוך קצר של BoT-SORT אם
הוא תואם למיקום Nano באותו זמן מקור, עם מראה תקין וללא מחלקה מתחרה.
רכישה ראשונית וחזרה מאובדן ממושך נשארות מחמירות; תחזית Nano אינה זיהוי.
שני זיהויי NEO עקביים בזמן SCAN יכולים לכוון סיבוב מוגבל לפני אישור מלא,
ללא התקדמות וללא הארכת תקציב החיפוש. הנחיית המועמד מוגבלת ל־800ms,
לאחריה 400ms ללא הנחיה נוספת; גבולות הזווית והזמן נשארים מחייבים.

בפייתון מופעל TCP_NODELAY בחיבורי השליטה והטלמטריה. קצב השליחה המבוקש
נשאר 20Hz ונשמרת בדיקת אישורי השרת. טלמטריה מנסה LISTEN עם GET כגיבוי
וכבדיקת חיות כשאין עדכונים. היא שולחת רק GET/LISTEN/UNLISTEN, ללא SET/ACTION.
זמני טלמטריה הם אומדן מקומי עם מרווח תקשורת, לא חותמות זמן מהרחפן.
MSDKRemote לא שונה. בדיקות localhost אינן מדידת ביצועי התקשורת עם הטלפון.

בעדכון `nano-template-3` נוסף רענון של התבנית הפנימית של Nano כאשר גודל
או מראה ה־NEO משתנים. נדרשים זיהוי YOLO חזק, אישור BoT-SORT, התאמה
למיקום ההיסטורי של Nano ופרטים חזותיים מספיקים. אין רענון מתוך חיזוי
Nano לבדו. הרענון מוגבל לפעם ב־750ms לכל היותר; אתחול מחדש בעקבות אובדן
או אי־התאמה פועל בנפרד. השיפור מיועד לרציפות חזותית ואינו מאריך את
הרשאת התנועה. מגבלות השליטה העדכניות מפורטות להלן.

אם המקלדת נחסמת עקב תשובת שרת נוספת או בלתי מזוהה, תוצג הודעה יציבה
שמנחה ללחוץ **Enable (E)**. הלחיצה מבצעת חיבור שליטה חדש ואימות פקודות
מחדש, בלי לשלוח שוב מקשים או פעולות שהיו ממתינים. Q / Esc או אובדן
מיקוד בזמן החיבור מונעים תנועה. כשל בחיבור עצמו עדיין מצריך ניסיון
חיבור נוסף; אין דילוג על בדיקת אישורי השרת.

בעדכון `nano-continuity-2` תוקנה הפסקת העקיבה בעקבות פקיעת הרשאת התנועה:
Nano ממשיך לעבוד על פריימי המצלמה גם לאחר פקיעת הרשאת התנועה. התיבה
מסומנת `UNVERIFIED` כל עוד אין אימות עדכני, ואינה מאשרת תנועה ב־guarded.
גם חריגה רגעית מ־100ms בעיבוד אינה מוחקת את תבנית המעקב. אובדן חזותי,
יציאה מהפריים, סתירה לזיהוי או תגובה נמוכה מתמשכת עדיין מפסיקים את העוקב.
ציון Nano הוא מדד עזר ולא הוכחה שהמטרה היא NEO; המשך תיבה אינו מדד לדיוק.
פער קטן בין תיבת Nano ל־Optical Flow יכול לחסום שליטה בלי למחוק את
העקיבה. כדי להסיק ממנו אובדן חזותי נדרשות נקודות זרימה עקביות ופער
משמעותי ביחס לגודל המטרה, משום שברחפן קטן הנקודות עלולות להיות מהרקע.
אירוע `nano_visual_rejected` מתעד את התיבה והמדדים שהובילו לפסילה.
גם אזור רקע בעל פרטים יכול לתת ציון Nano גבוה. חוסר התאמה מתמשך למראה
האחרון שאומת ב־YOLO מפסיק כעת את העקיבה אחרי 600ms; חזרת התאמה טובה
מנקה את החשד. זה עלול להפסיק גם עקיבה נכונה בעת שינוי זווית או מריחה
ממושכת. המנגנון אינו מבטיח עקיבה מרחוק לאורך כל הריקוד.

הוסרו קווי הסגמנטציה מהציור. המסכות נשמרות לעיבוד ולבדיקות המעקב.
ב־Analyzed frame מופיעים גם BoT-SORT בכחול ו־Nano בכתום מקווקו, כאשר
קיימת תוצאה מתאימה לזמן הפריים; Nano מסומן שם `HISTORICAL`. אין העתקה
של מיקום מפריים עתידי. ב־Live prediction ובסרטון החיזוי מוצגת העקיבה
החזותית העדכנית, כולל מצב `UNVERIFIED`. מצב Analyzed עדיין מתעדכן בקצב
YOLO; לצפייה בפריימי הביניים משתמשים ב־Live prediction.

קצב עדכוני Nano בפועל מופיע בחיווי. הוא מעבד את הפריים העדכני ביותר,
ואם העיבוד אינו עומד בקצב המצלמה הוא מדלג על פריימים במקום לבנות השהיה.
אין הבטחה ל־30FPS או לעקיבה רציפה כשאין בתמונה מספיק פרטים. בוטלו
אתחולים כפויים בכל חצי שנייה, ולאחר אתחול נלקח הפריים החדש ביותר.
ברירת המחדל כעת guarded; אפשר לבחור shadow להשוואת תצוגה ולוגים בלבד.

בעדכון `nano-guard-1` נוסף NanoTrack V2 על ה־CPU לצד YOLO ו־BoT-SORT.
מצב **shadow** מיועד לתצוגה ולוגים בלבד, ללא שינוי הרשאות התנועה.
ב־Settings אפשר לבחור `off`, `shadow` או `guarded` וללחוץ Apply.
לצפייה בתיבה בפריימי הביניים בחרו **Live prediction**. היא מסומנת `NANO`
ומציגה את גיל הפריים; זיהויי שתי המחלקות ומעקב BoT-SORT ממשיכים בנפרד.

`guarded` הוא מצב ניסיוני ושמרני: רק YOLO חזק, עם שיוך לזהות NEO של
BoT-SORT וללא סתירת מחלקה, יכול לאתחל או לחדש אימות. Nano אינו זיהוי NEO
ואינו מחדש את שעון האימות. נדרשים שני עוגנים חזקים שונים לאישור מחדש.
הרשאת גישור לסיבוב מוגבלת ל־400ms מפריים האימות ולפריים חזותי שגילו עד 100ms. הזמנים
נמדדים משעת הפענוח המקומית, ולא משעת החשיפה במצלמה שאינה זמינה בזרם. במהלך
גישור יכול לשמר התקדמות מאומתת קודמת בלבד עם דעיכה, עד 350ms מהמדידה
ועד 35% ממגבלת ציר ההתקדמות שהוגדרה. נדרשים מראה תקין, מרכוז וללא קרבה
או חיתוך בקצה; רוחב Nano אינו משמש להערכת מרחק. בחשד לרקע או יציאה
נחסם הגישור. SCAN עצמאי נשאר כפוף לזווית, לזמן ולכיוון רחפן עדכני.
לאחר פסילה חזותית נדרש אימות חדש מפריימים שפוענחו לאחר הפסילה.
פקיעת זמן לבדה חוסמת שליטה אך מאפשרת המשך עקיבה חזותית. השליטה הידנית נשארת זמינה.
זה אינו מנגנון למניעת התנגשות או אישור לביצוע ריקוד מהיר.

Nano משתמש בשתי משקולות נפרדות ב־`models/nanotrack_v2`, עם רישיון ו־SHA-256.
אין צורך ב־Setup חדש, CUDA או שינוי תלויות. מודלי YOLO וההגדרות השמורות
נשמרו; בהגדרה המקומית הועבר Nano ל־guarded לבקשת המשתמש. אירועי `nano_anchor`,
`nano_anchor_applied`, `nano_observation`, `nano_veto` ו־`nano_error`
מתעדים מקורות, זמנים, סיבת חסימה ועלות עיבוד. לוג פקודות כולל את הרשאת Nano.

קוצרה המתנה מיותרת לאחר ACK: מחזור השליחה נשאר לכל היותר 20Hz, אך זמן
האישור נכלל ב־50ms במקום להתווסף אליהם. תוצאת YOLO או Nano מעירה מיד
את הבקר; אין תור פריימים לעוקב, והעיבוד החוזר מוגבל. ציור התצוגה נעשה
בגודל החלון עם יחס תמונה שמור; Snapshot נבנה מחדש ברזולוציית המקור.
תוקנה גם הרשאת Dance הסופית עבור כל מודלי שתי המחלקות הרשומים והמאומתים.

## עדכון 1 — מגבלות נפרדות לארבעת צירי התנועה

במקום סליידר מהירות כללי קיימות ארבע מגבלות סופיות ונפרדות: למעלה/למטה,
סיבוב במקום, קדימה/אחורה ותנועה הצידה. כל מגבלה היא 0–100% מטווח ה־Virtual
Stick. היא מוכפלת בנקודת השליחה האחרונה גם במקלדת וגם ב־NEO Dance, ולכן
פקודת מעקב אינה יכולה לעקוף אותה. ערך 0 חוסם את הציר ו־100 מאפשר את כל הטווח.

בהתקנה על הגדרות ישנות נטענות ברירות המחדל השמרניות של השליטה הידנית הקודמת:
15% לסיבוב ו־1.5% לצירי התנועה. ניתן להעלות כל ציר עד 100% מהממשק. הערכים
נשמרים ב־`config.local.json` בעת חיבור, Apply או סגירה תקינה.

העדכון אינו מוסיף בדיקת קירות, חיישני מכשולים או מניעת התקרבות. התנהגות
הטיסה ליד קירות נשארת בשליטת הרחפן, MSDKRemote והפקודות שנשלחות.

מעבדת וידאו, זיהוי ומעקב עצמאית. מקבלת את זרם Mini 4 Pro דרך MSDKRemote ופורט TCP 9999. אינה דורשת את שרת ATLAS או את האתר. שליטה ידנית ומצב NEO Dance אופציונלי שולחים פקודות טיסה דרך TCP 9998, רק לאחר הפעלה מפורשת.

## מצב NEO Dance

כפתור אחד מחליף בין **START DANCE** לבין **STOP DANCE**. בחירת הריקוד עצמאית: אפשר לבחור אותה גם לפני חיבור או הפעלת שליטה, והיא נשמרת עד ללחיצה נוספת על הכפתור או סגירת התוכנית. כדי לשלוח תנועה נדרשים חיבור שליטה, Enable (E), וידאו וזיהוי עדכני מאותו טלפון. הכפתור מפעיל את אלגוריתם המרכוז, ההתקרבות ושמירת הגודל בתמונה שכבר קיים בפרויקט. הוא אינו ממריא אוטומטית ואינו מוסיף כוריאוגרפיה. רק מחלקה 0, `neo`, מורשית למעקב; `MINI PRO4` מוצגת כסיווג גולמי; חריג העמימות המוגבל מתואר לעיל. הסינון נשען על סיווג המודל ואינו מונע טעות סיווג שלו או מבחין בין שני רחפני NEO מאותה מחלקה.

התחלת ריקוד מאפסת את היסטוריית השליטה וממתינה למדידת `neo` חדשה לאחר ההפעלה. תנועה רגילה דורשת החלטה מגיל עד 200ms ומדידה מאושרת מגיל עד 250ms. באובדן `neo` נשמרים מנגנוני גרסה 12: חיזוי מוגבל בזמן וחיפוש המבוסס על מדידות קודמות ונתוני כיוון. זיהוי MINI PRO4 חד־משמעי אינו מחדש מדידה, ביטחון או תקציב חיפוש של `neo`. פתרון עמימות בעזרת זיכרון מחלקה מסומן בנפרד ואינו מחדש ראיה חזקה או תקציב חיפוש. וידאו/תוצאה שהתיישנו או שגיאת מודל חוסמים תנועה. מצב הריקוד הרציף נשאר ברירת המחדל; במצב חד־פעמי מפורש, STOPPED/SEQUENCE_DONE דורשים הפעלה מחדש.

רק **STOP DANCE** מכבה את בחירת הריקוד. החזקת מקשי תנועה נותנת קדימות למקלדת; שחרורם מחזיר לריקוד אוטומטית אם יש זיהוי תקין. Q/Esc, ניתוק או אובדן מיקוד החלון משחררים את סמכות השליטה, אך בחירת הריקוד נשמרת והחיווי מראה שהוא מושהה. E מחזיר סמכות שליטה בלי לשנות את הבחירה. F/R משהים פקודות תנועה בזמן פעולת המראה/נחיתה; לאחר סיום הפעולה יש ללחוץ E להמשך. Apply ואיפוס מעקב אינם מכבים את הבחירה. מעבר לכפתורי הטיסה או לסליידר אינו משחרר שליטה.

## מגבלות מהירות לפי ציר

בסרגל שמתחת לכפתורי השליטה מופיעים ארבעה סליידרים. במקלדת, לחיצה מלאה שולחת
את ערך המגבלה של הציר. ב־Dance, כוונת המעקב מוכפלת באחוז של אותו ציר. לכן,
לדוגמה, כוונת Forward של 0.30 עם מגבלה של 20% נשלחת כ־0.06. מאחר שכל כוונת
קלט מוגבלת מראש לטווח 1- עד 1+, הערך הוא גם חסם מוחלט לפקודה הסופית.

האחוז הוא אחוז מפקודת ה־Virtual Stick המנורמלת, לא מדידת מהירות במטרים לשנייה.
פקודות המראה ונחיתה אינן מושפעות מהסליידרים. הגדרות Yaw/Vertical/Forward
בחלק המעקב משפיעות על חישוב ה־Dance; מגבלות הצירים החדשות הן השער הסופי לפני
השליחה ומשפיעות גם על Dance וגם על המקלדת.

בחיפוש האוטומטי, העלייה לפקודת סיבוב מלאה מוגבלת בזמן. עצירה, בלימה ואובדן
אישור עדיין מקבלים קדימות מיידית; בדיקת BOOST המפורשת שומרת את התנהגות הבדיקה הקיימת.

בלוג נשמר אירוע `axis_speed_changed`. בכל `flight_command` נשמרים
`axis_limits`, הכוונה המקורית ב־`raw_values` והערכים שנשלחו בפועל ב־`values`.
`mode` מציין אם מקור הפקודה היה DANCE או MANUAL.

בלוג `events.jsonl` נוספים אירועי `control_mode`, `control_enabled`, `control_released`, `control_error` ו־`flight_command`. אירוע פקודה מכיל את מצב השליטה, ערכי הצירים ואישור השרת. אישור שרת אינו אימות התנועה הפיזית. `decision.intent` ו־`decision.command_sent` מתארים עדיין את שכבת החישוב בלבד; אירועי `flight_command` הם תיעוד השליחה המאושרת. מונה סוף הסשן סופר פקודות שקיבלו אישור בזמן הסשן. שליטה שהופעלה ללא סשן וידאו אינה נרשמת בלוג זה.

## שליטה ידנית במקלדת

הפעל בטלפון גם את Control Server, הזן Phone IP ולחץ **Connect keyboard**. אפשר לחבר שליטה בנפרד מהווידאו. לחץ **Enable (E)** להפעלת השליטה; לחיצה על תמונת הווידאו ממקדת את המקלדת. אין צורך בחבילת keyboard או בהרשאות מנהל.

| מקש | פעולה |
|---|---|
| E | הפעלת שליטה מהמקלדת |
| Q / Esc | איפוס התנועה ושחרור השליטה לשלט |
| W / S | עלייה / ירידה |
| A / D | סיבוב שמאלה / ימינה |
| ↑ / ↓ | קדימה / אחורה |
| ← / → | תנועה הצידה שמאלה / ימינה |
| F / R | המראה / נחיתה, רק לאחר הפעלת השליטה |
| X | סגירת התוכנית ושחרור השליטה |

העוצמות תואמות ל־FPVdemo: תנועה 0.015 וסיבוב 0.15. אפשר להחזיק כמה מקשים יחד; מקשים נגדיים מבטלים זה את זה. שחרור מקש מאפס את הציר. המראה ונחיתה נשלחות פעם אחת לכל לחיצה. מקשי הטיסה אינם פועלים בזמן הקלדה בשדות.

מעבר לחלון אחר או לשדה הגדרות משחרר שליטה; לחזרה נדרשת הפעלה מחדש ב־E. ניתוק וסגירה שולחים אפס ושחרור. אם עדכוני הממשק נעצרים ליותר מ־350ms, תהליך השליטה מבקש שחרור. שגיאת שרת מפסיקה את השליטה ומוצגת מתחת לכפתורים; יש לנתק ולהתחבר מחדש. בעת אובדן רשת אין אפשרות להבטיח שפקודת השחרור הגיעה — השתמש בשלט. ללא הפעלה מפורשת של NEO Dance המעקב משמש לתצוגה בלבד.

## עדכון והרצה ב־Windows

1. סגור את חלון Follow NEO.
2. חלץ את ZIP העדכון לתיקייה חדשה בתוך Downloads. אין לחלץ אותו ישירות על תיקיית הפרויקט.
3. בתיקייה שחולצה הפעל `UPDATE_ATLAS2_FOLLOW_NEO.cmd`.
4. חזור לתיקיית הפרויקט והתקן את התלויות המעודכנות. נדרש גם למי שכבר התקין גרסה 0.1.0:

```cmd
cd /d "C:\Users\Israel\Desktop\back_up_neo_drone_control\ATLASv2-main_ver1\tools\atlas2_follow_neo"
SETUP_FOLLOW_NEO.cmd
```

לאחר סיום ההתקנה:

```cmd
RUN_FOLLOW_NEO.cmd
```

ההפעלה השוטפת היא מתיקיית הפרויקט בלבד. אין צורך להפעיל סביבה ידנית או להשתמש ב־RUN_FROM_DOWNLOADS.

העדכון משנה רק קבצים מנוהלים בתוך `tools/atlas2_follow_neo`. לפני ההעתקה הוא שומר את הקבצים שיוחלפו ב־Downloads/ATLAS2_Follow_NEO_Backups. ההגדרות המקומיות, הלוגים וסביבת הפייתון נשמרים; SETUP מעדכן חבילות בתוך הסביבה הפרטית של הכלי בלבד. גיבוי העדכון הוא גיבוי קוד, לא צילום מלא של סביבת החבילות. אפליקציית Java של Yam וקבצי ATLAS שמחוץ לכלי אינם משתנים.

## בחירת המעבד

| בחירה | התנהגות |
|---|---|
| Auto | מנסה GPU; אם אתחול/בדיקת ההרצה נכשלו, עובר ל־CPU ומציג סיבה בממשק ובלוג. |
| GPU | מבקש GPU. כשל באתחול או בהקצאת המודל למנוע ההאצה הוא שגיאה גלויה; אין מעבר שקט ל־CPU. |
| CPU | הרצת ייחוס על המעבד. |

Windows משתמש ב־ONNX Runtime DirectML, התומך בחומרת DirectX 12 מיצרנים שונים. macOS משתמש ב־ONNX Runtime CoreML עם MLProgram ו־CPUAndGPU. אין צורך בהתקנת CUDA או TensorRT.

ב־Mac, CoreML רשאי לחלק את העבודה בין CPU ל־GPU. שיבוץ לגרף CoreML נבדק ב־profiling, אך אינו הוכחה שכל פעולה רצה פיזית על GPU. בממשק כתוב במפורש `CoreML / CPU + GPU permitted`. חלק מהפעולות יכולים להישאר על CPU גם ב־Windows.

`GPU adapter = -1` ב־Windows בוחר מבין מתאמי DXGI את בעל הזיכרון הייעודי הגדול ביותר, ללא בדיקת יצרן. ניתן לבחור אינדקס אחר; רשימת המתאמים ומזהיהם מופיעה ב־environment_check.json ובאירוע model_ready. ב־Mac בחירת המתאם נמסרת ל־CoreML והמספר אינו בשימוש.

בחירת המעבד והמתאם נעשית לפני Connect. אפשר לבדוק GPU בלי לחבר רחפן באמצעות:

```cmd
CHECK_GPU.cmd
```

הדוח נשמר ב־`logs/environment_check.json`. הכותרת PASS במצב Auto אינה הבטחה שהופעל GPU: בדוק את `compute.label` ואת `fallback_reason`. חבילות ההסקה אינן מותקנות בו־זמנית: SETUP מחליף את חבילת ONNX Runtime הישנה בזו המתאימה למערכת.

בבדיקה מ־10/10/2026 המחשב זוהה כ־GTX 1050 עם 4GB ודרייבר 582.66, ואומתה הרצת GPU ב־DirectML. ההתקנה אינה משנה דרייבר.

מקורות: [DirectML](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html), [CoreML](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html).

## חיבור ותצוגה

פתח MSDKRemote עם שרת הווידאו, הזן Phone IP ובחר H264/H265 בהתאם לזרם. סגור לקוחות וידאו אחרים שמחוברים לאותו שרת. לחץ Connect.

- **Analyzed frame:** תיבות `neo` בירוק ו־`MINI PRO4` בסגול, עם שמות וציון ביטחון, על הפריים שעליו חושבו. BoT-SORT בכחול ו־Nano היסטורי בכתום מוצגים כשיש תוצאה מתאימה לזמן הפריים. מסכות אינן מצוירות. גם תוצאה איטית נשארת גלויה, עם גיל הפריים בכותרת ואזהרת STALE כאשר הוא מתיישן. רק יעד `neo` שהתקבל מסומן SELECTED. נתוני Snapshot נקשרים לאותה תוצאה. זה המצב המתאים לבדיקת דיוק הזיהוי והמיקום.
- **Live prediction:** תיבות הזיהוי הגולמיות מוצגות עד גיל 750ms. אחרי 250ms הן מקווקוות ומסומנות `DELAYED` וגיל המדידה, ללא SELECTED. אלה מיקומים שנמדדו בפריים קודם והם עשויים לפגר אחרי תנועה. תיבת המעקב הכחולה עבור `neo` נשארת כפופה לחלון החיזוי הקיים; חיזוי מסומן PREDICTED. תוצאת זיהוי ריקה מנקה מיד את התיבות הגולמיות.

התוכנית שומרת את רזולוציית הזרם: מקור 1920×1080 נשאר כך במעקב, ב־Snapshot ובסרטונים. רק התצוגה מותאמת לגודל החלון. אין הקטנת וידאו ל־640×480. ערכי הרעש, השיוך והמהירות של הקלמן מותאמים לרזולוציה; יחידות המצב הן פיקסלים ברזולוציית המקור.

**קלט המודל נקבע לפי המודל שנבחר:** מודל `yolo26s_seg_best_mp4_v2.onnx` דורש `[1,3,640,640]`: פריים 1920×1080 מוקטן ל־640×360, עם 140 שורות שוליים מכל צד אנכי. המודל `yolo26s_seg_best_mp4_1920x1080_v2.onnx` דורש בפועל `[1,3,1088,1920]`: אותו פריים נכנס ללא הקטנה, עם 4 שורות שוליים למעלה ו־4 למטה. עבור מקור בגודל אחר נשמר יחס הממדים באמצעות letterbox. בשני המקרים התיבות והמסכות מוחזרות לקואורדינטות המקור. קובצי המשקלים נשמרים כפי שסופקו; שמות המחלקות מותאמים בתוך האפליקציה. המידות בפועל מופיעות בחיווי Model ובלוג `model_ready`.

## חלון מדידה ומעקב

- עד 250ms: תיקוני המרכוז המחושבים פועלים בעוצמתם הרגילה.
- בין 250 ל־300ms: תיקוני yaw וגובה המבוססים על המדידה דועכים לינארית לאפס.
- אחרי 300ms: תיבת המעקב הרגילה פגה, בכפוף לחריג החיזוי המוגבל הקיים. תיבות YOLO גולמיות משתמשות בחלון תצוגה נפרד כמפורט לעיל; הצגת תיבה אינה מאשרת פקודת תנועה.
- ביטחון המעקב המוצג ב־Live prediction דועך עם גיל המדידה, בדומה ל־C++; זה ציון מעקב נגזר ולא זיהוי YOLO חדש.
- חלון האיפוס לרכישת מסלול מחדש הותאם ל־750ms. מכונת המצבים יכולה לעבור ל־COAST/EDGE_RECOVERY/SEARCH; חלון התצוגה אינו זהה ל־timeout של החיפוש.
- `Result stale` הוא בדיקת תקינות הזרם/תוצאות, נפרדת מחלון 250–300ms.
- `STOPPED` הוא מצב שמור של בקר הריווח. הזיהוי יכול להמשיך במצב TRACK בעוד כוונת התנועה חסומה. כעת מופיעה דרישה מפורשת ל־Reset target / spacing.

הקלמן, החלקת המהירות, שיוך התיבות, אישור משתי מדידות, מרכוז עם אזור מת, השהיית היפוך כיוון, ריווח וחיפוש מחדש נשמרו. בדיקת נגיעה בקצה משתמשת כעת בתיבה הנמדדת ובשוליים של 2%, כפי שנעשה בחיבור המקורי ב־C++.

בטעינת הגדרות 0.1.0: חלון הרכישה מחדש מתעדכן ל־0.75 שניות; תקרת ההסקה הישנה של ברירת המחדל 15 מתעדכנת ל־60. יתר הגדרות המשתמש נשמרות. 60 הוא גבול לתזמון, לא הבטחה ל־60 FPS; אין הסקה חוזרת על אותו פריים כדי להעלות את המונה.

לאחר שינוי הגדרות מופיע `Changes pending — press Apply`. לחץ Apply + reset tracking להחלה. נזרקות תוצאות שהתחילו לפני האיפוס, כדי שלא יחדשו מסלול ישן.

## Snapshot והקלטות

ליד בחירת מצב התצוגה יש רשימה וכפתור פעולה:

| בחירה | פעולה |
|---|---|
| Snapshot | Save שומר PNG ו־JSON של התמונה המוצגת. |
| Clean video | Start מתחיל MP4 נקי מכל ציור; Stop מסיים ושומר. |
| Prediction video | Start מקליט וידאו חי עם תיבת קלמן לזמן הפריים ומצב המעקב. |
| Both videos | מקליט במקביל clean.mp4 ו־prediction.mp4 מאותו רצף פריימים. |

הסרטון המסומן מקליט תמיד את תצוגת Live prediction, בלי תלות בבחירת התצוגה שעל המסך, כולל תיבות גולמיות מאוחרות עם סימון DELAYED. ה־JSON הנלווה מפריד מדידה ותחזית ומתעד את גיל הזיהוי ואת סיבת הצגתו או הסתרתו. אפשר לבחור Snapshot ולצלם בזמן הקלטה; לעצירת ההקלטה בחר אחת מאפשרויות הווידאו ולחץ Stop.

המיקום: `logs/<session>/recording_<time>_<id>/`. נשמרים הסרטונים, `frames.jsonl` עם מזהי פריימים/זמנים/נתוני הסימון, ו־`recording.json` עם סיכום. ניתוק או סגירת החלון מסיימים ושומרים את ההקלטה לפני יציאה.

הקלטה מתבצעת ב־thread נפרד ובתור מוגבל. אם המחשב אינו עומד בקצב, שני הסרטונים מדלגים יחד על אותו פריים והמונה `skipped` עולה. זמני PTS משמרים את מרווחי הזמן המקומיים; אין שינוי מהירות הסרטון על ידי המצאת FPS קבוע. מקור הזמנים הוא הפענוח במחשב, לא זמן החשיפה במצלמה.

הסרטונים מקודדים H264 באיכות CRF 18 ובקידוד CPU מהיר; זו אינה שמירה ללא אובדן. הווידאו הנקי מתאים לאיסוף דאטה ללא סימונים. `Save raw video for this session` נשאר זמין לשמירת הזרם הדחוס המקורי, ללא קידוד חוזר, החל מההתחברות. הפענוח, ההקלטה והקלמן נשארים על CPU; ההאצה שנוספה מיועדת להסקת המודל.

## הפעלה ב־Mac

התלויות שנבחרו דורשות **macOS 13 ומעלה**, Python 3.12 עם Tk, ונתמכות בחבילות מוכנות הן ב־Apple Silicon והן ב־Intel. עדיף Python 3.12 מהמתקין הרשמי, הכולל Tk. אל תעתיק את תיקיית .venv מ־Windows.

להתקנת הקבצים מתוך תיקיית העדכון שחולצה ב־Downloads:

```bash
python3.12 apply_update.py --project "/absolute/path/to/ATLASv2-main"
```

בתיקיית `tools/atlas2_follow_neo` בפרויקט:

```bash
bash SETUP_FOLLOW_NEO.sh
bash RUN_FOLLOW_NEO.sh
```

בדיקת GPU:

```bash
.venv/bin/python run_lab.py --check --compute GPU
```

אין צורך בשרת ATLAS לצורך המעבדה. חיבור לתהליך Runtime של ATLAS ייעשה בהמשך דרך הממשקים המופרדים של detector/controller; אין לשתף את חיבור הווידאו הנוכחי עם לקוח נוסף במקביל.

## בדיקות ומגבלות

ב־Windows: `RUN_TESTS.cmd`. ב־Mac: `.venv/bin/python -m unittest discover -s tests -v`.

ראה VALIDATION_HE.md לתוצאות. GPU של המשתמש, macOS וחומרת הרחפן לא נבדקו בסביבת הפיתוח הזאת. אין הבטחה לקצב של 50FPS: קצב הזיהוי תלוי גם בקצב הפריימים שמגיע, בזמני הכנת הקלט, ב־GPU ובציור/הקלטה.
